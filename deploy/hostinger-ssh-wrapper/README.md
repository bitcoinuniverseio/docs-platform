# Hostinger forced command (review required)

This is a proposed root-run forced command for the dedicated CI key. It must receive independent security and protocol review before installation. The Python 3.9 wrapper and both template files are one audited unit; install them together as root-owned, non-writable files at `/usr/local/libexec/docs-deploy/`, with wrapper path `/usr/local/libexec/docs-deploy/wrapper.py`. The client change requires OpenSSH `scp -O`; SFTP, legacy SCP options other than the single receiver command, and other SSH commands are refused. The normal production workflow remains main-only.

The exact accepted expanded heredocs are [deploy.template](deploy.template) and [rollback.template](rollback.template), with `{sha}` a lowercase 40-hex SHA, `{target}` empty or a lowercase 40-hex SHA, root `/home/bitcoinuniverse/docs-releases` and KEEP `5`. Any byte difference is refused. The scripts are data, never executed. Deploy uses `/tmp/portal-<sha>.tgz` as a virtual name; uploads are stored as `.upload-<sha>` inside the release root. Only `scp -t /tmp/portal-<sha>.tgz`, `bash -s` with one exact template, and the five fixed curl commands in the scripts are accepted. Rollback performs its two fixed loopback curl calls internally. Public HTTPS verification stays on the runner.

Uploads are limited to 256 MiB, archive contents to 1 GiB and 50,000 members. Only regular files and directories are extracted; duplicates, traversal, links and special files are rejected. The root and its ancestors must be real directories owned by root and not group/world writable. Existing releases used by current or rollback must contain only root-owned regular files/directories, with no group/world write permission. This is stricter than the existing script's `chown bitcoinuniverse`; the web server needs read/search access, not write access. Existing symlinked assets or writable/user-owned releases require an independently reviewed migration before use. Existing SHA directories are refused, so redeploying an already retained SHA is unsupported. PREVIOUS and current are separately replaced; an interruption between the two atomic replacements may require operator repair. Pruning preserves current and PREVIOUS even when this retains more than five releases. A single lock serializes wrapper sessions; protect availability with SSH connection limits and timeouts.

## Operator installation and recovery

After independent review and separate production authorization, verify the root/ancestor and existing-release ownership, permissions, symlinks, web-server read access, Python and OpenSSH compatibility, disk capacity, and a recovery login. Back up the existing authorized_keys and release metadata. Install the three audited files under the root-owned path above, and configure **only the dedicated CI public key** with an authorized_keys forced command such as `restrict,command="/usr/bin/python3 -I /usr/local/libexec/docs-deploy/wrapper.py"`; retain a separate operator login. Ensure the process is root, the root directory exists and is root-controlled, and SSH does not permit environment or rc-file overrides. Do not apply this restriction to unrelated identities. Because the wrapper intentionally requires root-owned ancestors and releases, do not change production ownership blindly; review the effect on all other services first.

To undo installation, using the separate operator login restore the backed-up authorized_keys entry and restore the previous client version in a separately authorized release. If interrupted during switching, inspect the symlink and PREVIOUS manually and restore only validated retained SHA paths. Never use the CI key for recovery.

For a non-mutating dry run, run the test suite below on an isolated local fixture. In staging with a disposable key and fixture release root configured in a copy of the wrapper, exercise upload and deploy there, not against production `current`. With the CI identity only, verify `ssh host id`, `ssh host 'bash -c id'`, `sftp host`, and an SCP upload to a different destination all fail; verify the approved loopback curl commands separately. Do not use a production deploy as a dry run. Exact template verification is pinned to the checked-out scripts; changes to either script require a coordinated wrapper update and review.
