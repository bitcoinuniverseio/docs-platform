# Hostinger docs deployment forced command

This change requires independent security and operational review before installation. Nothing here installs or deploys it. The audited entry point is `/usr/local/libexec/docs-deploy/wrapper.py`; its two adjacent `.template` files are part of the trusted code. Python 3.9+ and `/usr/bin/curl` are required.

The client change uses `scp -O`: this is the narrowly scoped legacy SCP receiver protocol, not modern SFTP. OpenSSH clients must support `-O`; servers must pass `scp -t /tmp/portal-<40 lowercase hex>.tgz` unchanged to the forced command. Only one SCP C record is accepted, with no metadata or directories. The virtual `/tmp` destination is never opened: data goes to `.upload-<sha>` inside the release root. Other SCP commands and all SFTP subsystems are refused. No legacy SCP fallback or shell is exposed.

`bash -s` accepts exactly the byte-for-byte expanded [deploy.template](deploy.template) or [rollback.template](rollback.template), including their final newline. The only substitutions are root `/home/bitcoinuniverse/docs-releases`, lowercase 40-hex SHA, KEEP `5`, and rollback TARGET empty or lowercase 40-hex. These scripts are never executed. The trusted Python code performs their operations. The only other commands are the five fixed loopback curl strings in `wrapper.py`: status for `/`, `/protocols/`, `/pagefind/pagefind.js`, `/RELEASE`, and content for `/RELEASE`. Rollback runs its two fixed checks internally. Any change to a client heredoc requires review and a matching template update. Nondefault RELEASES or KEEP is unsupported.

Uploads are limited to 256 MiB; archives to 50,000 entries and 1 GiB of declared expanded regular-file data. Only regular files and directories are supported; links, devices, absolute paths and traversal are rejected. Existing SHA releases are immutable and reused for retries; unlike the old script, they are not overwritten. Extraction normalizes permissions to web-readable files and directories, owned by the wrapper user. Retention keeps the five newest plus the current and previous release when necessary. `current` replacement is atomic; writing PREVIOUS is a separate atomic replacement, so a crash between those operations may require operator repair. A pre-existing `current.new` causes refusal. There is no automatic health-check rollback. Wrapper operations serialize through a lock; other privileged processes must not mutate this tree concurrently.

## Operator installation after review

1. First ensure a separate, tested recovery login and back up the existing authorized-keys entry and release state. Verify the account used for this forced command can execute as root; the wrapper deliberately refuses an untrusted release root. The SSH key must have no other unrestricted login path, and password authentication must not bypass this restriction. A root forced command remains security-sensitive and requires review of the root-owned code and server SSH configuration.
2. On the host, audit the entire release root and its ancestors: each must be a real root-owned directory with no group or other write permission. Audit existing retained release directories and their content, migrate them to root ownership and remove non-root write access, and verify web-server read/traverse permissions. Ensure `current` is absent or an absolute symlink to a retained 40-hex directory under the root, and PREVIOUS is `none` or such an absolute path. Remove any stale `current.new` only after checking it. Do not apply these ownership changes blindly to a shared home directory; if this trust boundary cannot be established, do not install.
3. Install the reviewed `wrapper.py`, `deploy.template`, and `rollback.template` at `/usr/local/libexec/docs-deploy/`, root-owned and not writable by the SSH identity or other non-root users. Configure the CI key's authorized_keys entry with `restrict,command="/usr/bin/python3 /usr/local/libexec/docs-deploy/wrapper.py"` and retain an independent recovery access path. Ensure the SSH daemon permits the forced command and no SSH configuration overrides it. This must be performed by an authorized operator, not the coding worker.
4. Test with **the CI identity only**: `ssh ... 'id'`, `ssh ... 'bash -c id'`, `ssh ... 'scp -t /etc/passwd'`, and `sftp ...` must all fail. A fixed curl check may be tested without changing state. For a deployment dry run that does not alter `current`, run the local temporary-fixture tests below; do not send a deployment script to production as a dry run. Check `current` and PREVIOUS before and after any operator validation.
5. Promote the client change separately before relying on the restricted key. Main promotion and a real deployment require separate operator authorization. Preserve the independent review.

To undo the restriction, use the separate recovery login to restore the backed-up authorized-keys entry and verify access. Do not modify `current` as part of key rollback. If a release must be reverted, use the separately authorized normal rollback procedure after checking retained releases and PREVIOUS.

## Focused local verification

Run `python3 -m unittest discover -s deploy/hostinger-ssh-wrapper -p 'test_*.py' -v`. Tests use temporary directories and mocked curl; they do not connect to Hostinger or alter a live release. The test suite checks the current client heredoc expansion against the pinned templates. Independent review must additionally assess the SCP parser, archive handling and host trust boundary before use.
